# STORY-04-03-01: Implement Review-Queue Endpoints

*Parent feature: [FEATURE-04-03 — Operator Review-Queue API](../FEATURE-04-03-operator-review-queue-api.md) · Parent epic: [EPIC-04 — Backend Application & API](../../EPIC-04-backend-application-and-api.md)*

This is the **first of the two** stories in FEATURE-04-03 (Operator Review-Queue API). It specifies the **review-queue list and resolve endpoints** over the `review_queue` table — the surface through which the single seeded operator clears the items the EPIC-03 matcher routed out of the auto-commit path: low-confidence extractions and matches (the `n<5` matches surfaced per PRD §8.5), brand-new clusters, and duplicate-merge candidates (PRD §8.6 names this the core operator loop and the main defense against catalog fragmentation). Per `docs/schema.sql`, the `review_queue` row carries `id` (BIGINT identity primary key), `kind` (`review_kind` — `extraction` / `match` / `new_cluster` / `merge_candidate`), `ref_table`, `ref_id`, `reason`, `payload` (JSONB), `state` (`review_state` — `open` / `resolved` / `dismissed`, NOT NULL DEFAULT `open`), `created_at`, `resolved_at`, and `resolved_by`; that schema defines no UNIQUE constraint and no database-level state guard on this table, so the resolve transition is enforced as a single atomic conditional update keyed on `state = 'open'` in the application layer.

The resolve endpoint is **action-driven**: the request body carries an `action` ∈ { `approve`, `correct`, `dismiss`, `confirm`, `merge` }, and the resulting `review_queue.state` is **derived from the action** (`dismiss` → `dismissed`; every other action → `resolved`) rather than supplied as a free `state` value. Each action carries its own side effect, and **the side effect and the `review_queue` state transition execute inside one database transaction** so the item is never marked resolved without its corrective write landing: `approve` (kind `extraction`/`match`) sets the referenced `sale_observation.match_status = 'reviewed'` and leaves `excluded_from_comps = FALSE`; `correct` applies the operator's `corrections` (for example `variation_id`, `grade_id`) to the referenced `sale_observation` row and sets `match_status = 'reviewed'`; `dismiss` (a `match`) sets `sale_observation.match_status = 'rejected'` and `excluded_from_comps = TRUE`; `confirm` (kind `new_cluster`) retains the candidate `variation` referenced by `ref_id` as a catalog row; and `merge` (kind `merge_candidate`) repoints every `sale_observation` (and `card_character`) from the duplicate `ref_id` to the surviving canonical id named in `merge_target_id` and tombstones the duplicate. The endpoints build on the FEATURE-04-01 API scaffolding: each handler opens a short-lived Neon connection through the **pooled** `DATABASE_URL` and never the unpooled `DATABASE_URL_UNPOOLED` (which EPIC-02 reserves for DDL and migrations), threads the operator `userId` from the `getUserId()` seam (v1 = the single seeded operator, `resolved_by` is backed by `app_user.id`), validates input and returns HTTP **400** with a named `error` field (through the shared safe error envelope defined in `STORY-04-01-03`) on malformed input before any database access, issues no LLM call in the request path, sources data through official APIs only, and is gated to the operator role (full role-based authentication is deferred).

## User Story

> **As an** Operator, **I want** to list and resolve `review_queue` items, **so that** I can approve/correct low-confidence extractions and matches, confirm new clusters, and clear merge candidates that the automated matcher routed for review.

## API Contract

### List — `GET /api/operator/review-queue`

- **Query parameters:** `state` ∈ {`open`, `resolved`, `dismissed`} (optional, default `open`), `kind` ∈ {`extraction`, `match`, `new_cluster`, `merge_candidate`} (optional), `limit` ∈ [`1`, `100`] (optional). A `state` outside its set returns HTTP **400** `{ "error": "state" }`; a `kind` outside its set returns HTTP **400** `{ "error": "kind" }`; both are checked before any read. Parameters and the safe error envelope are governed by the shared validator in [STORY-04-01-03](../FEATURE-04-01/STORY-04-01-03-implement-query-parameter-validation.md).
- **Response** (HTTP **200**): a JSON array of items, each `{ "id", "kind", "ref_table", "ref_id", "reason", "payload", "state", "created_at", "resolved_at": null, "resolved_by": null }`. An empty result is `[]` (never HTTP 404). The EPIC-05 review-queue workbench ([STORY-05-03-03](../../EPIC-05/FEATURE-05-03/STORY-05-03-03-implement-review-queue-workbench-ui.md)) calls this exact path.

### Resolve — `PATCH /api/operator/review-queue/{id}`

- **Path parameter:** `id` must be a positive BIGINT; a malformed (non-numeric / wrong-shape) or non-positive `id` returns HTTP **400** `{ "error": "id" }` **before any database access**.
- **Request body:** `{ "action": <approve|correct|dismiss|confirm|merge>, … }`. An `action` outside the set returns HTTP **400** `{ "error": "action" }`. Action-specific fields: `correct` carries `corrections` (an object of `sale_observation` columns to set, for example `variation_id`, `grade_id`); `merge` carries `merge_target_id` (the surviving canonical id). The derived target state is `dismissed` for `dismiss` and `resolved` for every other action.
- **Side effects (one transaction with the `state = 'open'`-guarded conditional update):**

  | `action` | Applicable `kind` | Side effect | Resulting `state` |
  |----------|-------------------|-------------|-------------------|
  | `approve` | `extraction`, `match` | referenced `sale_observation.match_status = 'reviewed'`; `excluded_from_comps` stays `FALSE` | `resolved` |
  | `correct` | `extraction`, `match` | apply `body.corrections` to the referenced `sale_observation`; `match_status = 'reviewed'` | `resolved` |
  | `dismiss` | any (`match` shown) | `sale_observation.match_status = 'rejected'`, `excluded_from_comps = TRUE` | `dismissed` |
  | `confirm` | `new_cluster` | retain the candidate `variation` referenced by `ref_id` as a catalog row | `resolved` |
  | `merge` | `merge_candidate` | repoint every `sale_observation` and `card_character` from the duplicate `ref_id` to `merge_target_id`; tombstone the duplicate | `resolved` |

  Every action stamps `resolved_at = now()` and `resolved_by = getUserId()`.
- **Response** (HTTP **200**): `{ "id", "state", "action", "resolved_at", "resolved_by", "affected": { "table": "sale_observation", "ids": [9001, 9002] } }`, where `affected` reports the table and row ids the side effect touched.
- **Errors:** malformed/non-positive `id` → HTTP **400** `{ "error": "id" }`; invalid `action` → HTTP **400** `{ "error": "action" }`; unknown `id` → HTTP **404**; an item already `resolved`/`dismissed` (including the losing request of a concurrent pair, whose `state = 'open'`-guarded update matches zero rows) → HTTP **409**. All errors return the shared safe error envelope from [STORY-04-01-03](../FEATURE-04-01/STORY-04-01-03-implement-query-parameter-validation.md): a stable public `error` field only, with no stack trace, SQL, connection string, secret, or internal exception message exposed.

## Acceptance Criteria

1. **(valid-output — LIST default open)** **Given** `review_queue` holds items in `state = open` and items in `state = resolved`, **When** the operator calls `GET /api/operator/review-queue` with no `state` query parameter, **Then** the response is HTTP **200** and every returned item has `state = open`, with no item in `state = resolved` or `state = dismissed` present.
2. **(valid-output + input-validation — LIST explicit filter and invalid state)** **Given** `review_queue` holds items across `state = open`, `state = resolved`, and `state = dismissed`, **When** the operator calls the list endpoint with `state=resolved`, **Then** the response is HTTP **200** and every returned item has `state = resolved`; **and given** a `state` query value outside the set { `open`, `resolved`, `dismissed` } (for example `archived`), **Then** the response is HTTP **400** with an `error` field that names `state`, and no read is issued.
3. **(valid-output — RESOLVE approve/correct/dismiss side effects and stamping)** **Given** an `open` item of kind `extraction` or `match`, **When** the operator `PATCH`es it with `action = approve`, **Then** the response is HTTP **200**, the referenced `sale_observation.match_status` becomes `reviewed` with `excluded_from_comps` left `FALSE`, the `review_queue.state` becomes `resolved`, and `resolved_at = now()` / `resolved_by = getUserId()` are stamped; an `action = correct` additionally applies `body.corrections` to the `sale_observation` before setting `match_status = reviewed`; and an `action = dismiss` sets `sale_observation.match_status = rejected` with `excluded_from_comps = TRUE` and `review_queue.state = dismissed`.
4. **(valid-output — RESOLVE confirm/merge side effects in one transaction)** **Given** an `open` `new_cluster` item, **When** the operator `PATCH`es it with `action = confirm`, **Then** the candidate `variation` referenced by `ref_id` is retained as a catalog row and `state` becomes `resolved`; **and given** an `open` `merge_candidate` item resolved with `action = merge` and a `merge_target_id`, **Then** every `sale_observation` and `card_character` row is repointed from the duplicate `ref_id` to `merge_target_id` and the duplicate is tombstoned, with the side effect and the `state → resolved` transition committed in **one transaction** (a failure of either rolls back both).
5. **(input-validation — invalid action)** **Given** a resolve request whose `action` is outside the set { `approve`, `correct`, `dismiss`, `confirm`, `merge` } (for example `archive`), **When** the request is processed, **Then** the response is HTTP **400** with an `error` field that names `action`, and zero rows in `review_queue`, `sale_observation`, or `card_character` are modified.
6. **(input-validation — malformed or non-positive id)** **Given** a resolve request whose path `id` is malformed (non-numeric, wrong shape, or non-positive, for example `abc` or `-1`), **When** the request is processed, **Then** the response is HTTP **400** with an `error` field that names `id`, returned **before any database access**, and zero rows are modified.
7. **(error-handling / edge-case — unknown id and concurrency)** **Given** an `id` that matches no `review_queue` row, **When** the operator resolves that `id`, **Then** the response is HTTP **404** with a named `error` field and zero rows are modified; **and given** an item already `resolved`/`dismissed` — including the losing request of two concurrent resolves of the same `open` `id`, whose `state = 'open'`-guarded update matches zero rows — **Then** the response is HTTP **409** with `resolved_at` and `resolved_by` left unchanged, while exactly one concurrent request transitions the row and returns HTTP **200**.
8. **(input-validation — unknown kind filter)** **Given** a list request whose `kind` query parameter is a value outside the set { `extraction`, `match`, `new_cluster`, `merge_candidate` }, **When** the request is processed, **Then** the response is HTTP **400** with an `error` field that names `kind`, and no rows are returned.

## Edge Cases

- **Empty/Null — empty queue for the requested state:** `review_queue` holds zero items in the requested `state` (for example no `open` items remain) → the list endpoint returns HTTP **200** with an empty JSON array `[]`, not HTTP **404**.
- **Invalid — already-resolved item:** a resolve request targets an item whose `state` is already `resolved` or `dismissed` → HTTP **409**, and the stored `resolved_at` and `resolved_by` are left unchanged.
- **Concurrent — same item resolved at the same time:** two operators resolve the same `open` `id` at the same time → the atomic conditional update keyed on `state = 'open'` lets exactly one request transition the row and return HTTP **200**; the other matches zero rows and returns HTTP **409**.
- **Boundary/Invalid — unknown kind or state filter:** a list `kind` value outside { `extraction`, `match`, `new_cluster`, `merge_candidate` } → HTTP **400** `error = kind`; a list `state` value outside { `open`, `resolved`, `dismissed` } → HTTP **400** `error = state`; no rows are returned in either case.
- **Invalid — malformed/non-positive id or unknown action:** a resolve path `id` that is non-numeric, wrong-shape, or non-positive → HTTP **400** `error = id` before any database access; a body `action` outside { `approve`, `correct`, `dismiss`, `confirm`, `merge` } → HTTP **400** `error = action`; zero rows in `review_queue`, `sale_observation`, or `card_character` are modified.

## Story Estimation Guidance

- **Effort: High** — a filtered list handler plus an action-dispatching resolve handler that, across five `action` branches, writes `review_queue`, `sale_observation`, `variation`, and `card_character` inside one transaction, including the `merge` repoint of `sale_observation`/`card_character` to a surviving canonical id.
- **Complexity: High** — the resolve transition must be a single atomic conditional update keyed on `state = 'open'` because `docs/schema.sql` defines no UNIQUE constraint and no database-level state guard; the concurrent-resolution path must yield exactly one HTTP 200 winner with the loser receiving HTTP 409; and each action's side effect must commit or roll back together with the state transition.
- **Uncertainty: Medium** — the side-effect contract is fixed by `docs/schema.sql` and PRD §8.6, but the request/response shape depends on the FEATURE-04-01 scaffolding, which is unbuilt, so the exact validation-error and `affected` shapes settle once that foundation lands.
- **Fibonacci Story Points: 8.** The five-action dispatcher, the cross-table transactional side effects (notably the `merge` repoint), the concurrency-safe transition, and the multi-path validation place this at an 8; the fixed schema and single-operator gating hold it from rising further. Points measure relative size, not a duration.
